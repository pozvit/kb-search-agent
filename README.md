# KB Search Agent

Агент отвечает на вопросы по базе знаний компании: продукты, проекты, кейсы и их показатели. Он ищет подходящие фрагменты документов и строит ответ только по ним, со ссылками вида `[Фрагмент N]` на документ, файл и номер чанка. Если в документах ответа нет, агент так и говорит.

Проект продолжает RAG-пайплайн с предыдущих этапов курса (его описание в [docs/rag_pipeline.md](docs/rag_pipeline.md)). В пайплайне был один фиксированный путь «вопрос, поиск, ответ». В агенте модель сама решает, вызывать ли инструмент и с какими аргументами, а код агента проверяет её решения, обрабатывает отказы и не даёт выдать ответ, не подкреплённый найденными фрагментами.

## Возможности

| Запрос | Что делает агент | Инструмент |
|---|---|---|
| Вопрос по фактам: «Какие решения входят в цифровое ядро AIMS?» | ищет и отвечает со ссылками на фрагменты | `search_knowledge_base` |
| Вопрос с параметром: «…top_k=6» | использует заданное значение, некорректное отклоняет | `search_knowledge_base` |
| Перечисление по реестрам: «какие проекты были в медицине», «перечисли пропозалы за 2019–2021» | выдаёт полный список карточек по отрасли, периоду и типу, без вызова модели | `list_cards` |
| Люди по прошлому ответу: «кто выполнял эти проекты» | команда, партнёр и имя сотрудника по каждой карточке прошлого ответа, без вызова модели | `list_cards` |
| Карточки сотрудника: «Проекты Сотрудник за последние 5 лет», «что делал Петров в 2025 году» | список карточек с фильтром по человеку и периоду, без вызова модели | `list_cards` с `person` |
| Подсчёт: «кто делал много проектов в операционной эффективности», «топ сотрудников по digital» | рейтинг людей по числу карточек, проекты и пропозалы отдельно, без вызова модели | `list_cards` с `group_by="people"` |
| Вопрос по реестрам с темой: «проекты по закупкам в медицине» | ищет по смыслу с фильтрами по категории, годам и отрасли | `search_knowledge_base` |
| «Какие документы есть в базе?» | перечисляет документы и категории | `list_documents` |
| Уточнение: «А сроки там какие?» | берёт тему из предыдущего вопроса | `search_knowledge_base` |
| Вопрос, ответа на который в документах нет | отвечает «Недостаточно информации в предоставленных документах.» | `search_knowledge_base` |
| Приветствие | отвечает одной фразой, поиск не запускает | — |

Инструменты находятся в `src/agent_tools.py`.

`search_knowledge_base(query, top_k=4, category=None, year_from=None, year_to=None, industry=None)` кодирует запрос моделью `multilingual-e5-small` и ищет ближайшие чанки в Qdrant. Аргументы проверяются: `query` не пустой и не длиннее 500 символов, `top_k` целое от 1 до 10 (строка `"3"` принимается, `2.5`, `True` и `"пять"` нет), `category` и `industry` должны существовать в индексе (отрасль сравнивается без учёта регистра), годы от 1900 до 2100. Фильтр по годам выбирает карточки, период которых пересекается с заданным. Фильтры по году и отрасли работают только для карточек реестров: у коммерческих предложений и описаний продуктов таких полей нет.

Допустимые категории, отрасли и диапазон лет агент берёт из индекса при первом запросе и подставляет в описание инструмента, чтобы модель выбирала значения из списка. У каждой отрасли там же указаны русские синонимы («Pharma & HC: медицина, здравоохранение, фармацевтика…»). Неточное значение от модели сопоставляется со списком по вхождению, основам слов и синонимам. Если сопоставить не удалось, агент повторяет поиск без этого фильтра и пишет об этом в предупреждении: ошибка в фильтре, придуманном моделью, не должна оставлять пользователя без ответа.

`list_cards(card_type, industry, service, person, year_from, year_to, include_people, group_by)` выбирает из каталога карточек (`data/raw_cards/cards_meta.jsonl`) все карточки по условиям, до 50 в одном ответе. Поиск по смыслу возвращает не больше 10 самых похожих фрагментов, поэтому для перечислений он не подходит: на вопрос «какие проекты были в медицине» он давал 5 карточек из 18. Фильтр `service` принимает тип услуги (8 типов, например «Операционная эффективность») или детальный тег (60 тегов, например «Закупки / управление поставщиками»). `group_by="people"` строит рейтинг людей: человек считается один раз на карточку по полям «Команда», «Партнёр / директор», «Имя сотрудника»; запись без инициалов и латинская запись («Sidorenko Alexey») объединяются с полной, если фамилия однозначна, а у латинской записи совпадает инициал; сортировка по числу проектов, потому что пропозал — заявка, а не выполненная работа. Каталог доступен в профиле `full`.

`list_documents()` проходит по payload коллекции без загрузки векторов и возвращает документы, их категории и число чанков, а также сводку по категориям и годам.

Оба инструмента возвращают словарь со `status: "success"` или `status: "error"` с полями `error_code` и `error` и не выбрасывают исключений. Коды ошибок: `invalid_argument`, `index_unavailable`, `unknown_tool`, `internal_error`.

## Как работает

```
запрос
  → проверки до модели: пусто, слишком длинно, секреты, явный top_k
  → LLM выбирает инструмент и аргументы
  → инструмент выполняет поиск
  → LLM формирует ответ по найденным фрагментам
  → проверка ответа: ссылки на существующие фрагменты, числа есть в тексте фрагментов
  → ответ, источники, trace
```

Все развилки с условиями перечислены в [scenario.md](scenario.md), сценарии проверки с критериями лежат в `config/agent_scenarios.yaml`.

Решения, которые стоит знать при чтении кода:

1. Модель вызывается через нативный API Ollama `/api/chat`. OpenAI-совместимый `/v1` не принимает параметр `num_ctx`. Промпт агента на ответном шаге занимает около 2 500 токенов, и при меньшем окне Ollama обрезала бы его без предупреждения. Окно 8192 передаётся в каждом запросе, отдельный Modelfile не нужен.
2. `temperature` равна 0, `seed` равен 42, чтобы выбор инструмента был воспроизводимым.
3. Если пользователь сам указал `top_k=0`, агент не исправляет значение молча. Инструмент возвращает ошибку, и пользователь её видит.
4. Когда инструмент завершился ошибкой, текст ответа берётся из шаблона в `agent_prompts.py`. Модель в этот момент не вызывается и не может написать «готово».
5. Если на вопрос по базе модель ответила без вызова инструмента, агент выполняет поиск сам и отмечает это в trace как `forced_search`. В боевом прогоне так было в 3 шагах из 13.
6. Иногда qwen2.5 присылает вызов инструмента текстом `<tool_call>{...}</tool_call>`, а не отдельным полем. Такой вызов разбирается из текста.
7. Для уточняющего вопроса («а…», «там», «этом») агент дописывает в поисковый запрос названия из предыдущего вопроса, если модель их пропустила. Без этого в первом боевом прогоне qwen2.5 ответила на уточнение про SIPS верно, но не включила название продукта в поисковый запрос, и сценарий `recovery_followup` не прошёл.
8. После ответа агент запоминает, на какие карточки реестров он ссылался. Если следующий вопрос относится к ним («кто делал эти проекты», «по ним», короткое «А по людям?» без новой отрасли, года или типа реестра), поиск идёт только по этим карточкам. Модель может запросить то же самое параметром `previous_results`. Без этого вопрос «кто делал эти проекты» искался по всей базе и находил посторонние коммерческие предложения.
9. Перечисления и вопросы о людях по прошлому ответу обрабатывает программный маршрутизатор, без вызова модели. Если вопрос начинается с «какие», «перечисли», «сколько» и т. п., говорит о проектах или пропозалах и задаёт отрасль, период или тип, агент выбирает карточки из каталога и сам форматирует список. Отрасль распознаётся по русским синонимам категорий. Если в вопросе есть другая тема («по закупкам»), маршрутизатор его не берёт: нужен поиск по смыслу. Ответ получается полным и приходит за доли секунды вместо 2–3 минут работы модели на CPU.
10. Переменные `LLM_API_KEY` и `LLM_BASE_URL` из `.env` относятся к YandexGPT из прошлого этапа. Агент их не читает, поэтому ключ Yandex не уходит на локальный эндпоинт.

```
  agent_tools.py           search_knowledge_base, list_documents, list_cards, escalate_to_human, адаптер к Qdrant
  agent_llm.py             клиент Ollama и детерминированная mock-модель
  agent_guardrails.py      проверки запроса до обращения к модели

  agent_lexical.py         BM25 по chunks.jsonl для прогонов без модели эмбеддингов

  agent_evaluator.py       проверки ответа по критериям сценария
  scenario_runner.py       прогон сценариев и запись отчётов
  build_index.py           сборка индекса одной командой

```

Файлы пайплайна (`pipeline.py`, `retriever.py`, `rag_answer.py` и другие) описаны в `docs/rag_pipeline.md`, обработка реестров проектов и пропозалов — в его разделе 16. Для агента в них внесены изменения: `Retriever.retrieve` принимает необязательный фильтр, три пайплайна принимают путь к конфигу аргументом, `vector_indexer.py` надёжно пересоздаёт коллекцию на Windows (подробности в разделе «Ограничения»), склейка строк при очистке применяется только к PDF, `chunk_pipeline.py` добавляет в чанки метаданные карточек реестров.

## Установка

Нужны Python 3.10 или новее и [Ollama](https://ollama.com).

```bash
python -m venv .venv
source .venv/bin/activate            # Windows: .venv\Scripts\activate
pip install -r requirements.txt

ollama pull qwen2.5:7b-instruct      # около 4,7 ГБ

python src/build_index.py --profile public
```

Последняя команда собирает индекс по пяти PDF из `data/raw`: 49 чанков. Если модель эмбеддингов уже скачана, сборка занимает около 10 секунд. При первом запуске команда скачивает `intfloat/multilingual-e5-small` (471 МБ) с Hugging Face.

Для проверки без Ollama и без модели эмбеддингов достаточно `pip install PyYAML PyPDF2 pytest` и `python src/build_index.py --profile public --no-embed`. Так работают тесты и прогон сценариев в режиме `--llm mock --retriever lexical`.

## Переменные окружения

Ключи API не нужны. Все переменные необязательны, значения по умолчанию заданы в `config/agent.yaml` (шаблон в `.env.example`):

```
AGENT_LLM_BACKEND=ollama              # ollama или mock
AGENT_LLM_BASE_URL=http://localhost:11434
AGENT_LLM_MODEL=qwen2.5:7b-instruct
AGENT_RETRIEVER=qdrant                # qdrant или lexical
AGENT_PROFILE=public                  # public или full
RAG_EMBEDDINGS_ALLOW_DOWNLOAD=1       # 0 — модель эмбеддингов только из локального кэша
ESCALATION_QUEUE_PATH=data/escalations/escalations.jsonl
LOG_LEVEL=INFO                        # DEBUG, INFO, WARNING, ERROR
LOG_FORMAT=json                       # json или text
```

Полный список с пояснениями — в `.env.example`. Тест `tests/test_configuration.py` проверяет, что в шаблоне описана каждая переменная, которую читает код, а у ключей и токенов в шаблоне нет значений.

Флаги командной строки имеют приоритет над переменными окружения, переменные над `agent.yaml`.

Модель эмбеддингов загружается из локального кэша Hugging Face без обращения к сети. В сеть агент идёт, только если модели в кэше нет, то есть при первом запуске. Чтобы запретить и это, задайте `RAG_EMBEDDINGS_ALLOW_DOWNLOAD=0`: тогда без скачанной модели сборка индекса и поиск завершатся понятной ошибкой. Телеметрия библиотек Hugging Face отключена. Тексты запросов и документов никуда не отправляются: эмбеддинги считаются локально, модель работает в локальной Ollama, индекс хранится в локальном Qdrant.

## Запуск

```bash
python src/agent_cli.py                                   # диалог
python src/agent_cli.py -q "Какие три цифровых решения входят в цифровое ядро AIMS?"
python src/agent_cli.py -q "..." --show-trace             # trace в консоль
python src/agent_cli.py -q "..." --save-trace             # trace в data/agent/traces/
python src/agent_cli.py --llm mock --retriever lexical    # без Ollama и torch
python src/agent_cli.py --profile full                    # полная база, только локально
```

В диалоге работают команды `/reset` (очистить память), `/memory`, `/trace` (trace последнего ответа) и `/exit`.

Пример ответа (mock-модель, режим lexical):

```
По данным базы знаний:
3. Что такое AIMS AIMS (Asset Intelligence Management System 2.0) — интеллектуальная система
управления имуществом на базе цифровых решений. [Фрагмент 1]
Цифровое ядро:
• цифровой паспорт актива — …;
• цифровой пульс актива — …;
• цифровая биржа имущества — … [Фрагмент 1]

Источники:
  [Фрагмент 1] AIMS — Asset Intelligence Management System 2.0 — 03_aims_asset_management.pdf, чанк 4

[answered] маршрут: tools | LLM: 2 | tools: search_knowledge_base(ok) | память: 2
```

Скорость на CPU (замеры из `data/agent/scenario_report_ollama.json`, qwen2.5:7b-instruct): вызов модели для выбора инструмента занимает 3–8 секунд при промпте около 780 токенов, вызов для ответа 21–48 секунд при промпте 1 000–2 500 токенов. Обычный вопрос отвечается за 30–60 секунд. Первый запрос после запуска Ollama дольше на время загрузки модели в память. Параметр `keep_alive: 30m` держит модель загруженной между запросами.

## Проверка

```bash
pytest                                                          # 99 тестов, около секунды

python src/agent_cli.py --run-scenarios --llm mock --retriever lexical
# отчёты: data/test_results.json, data/agent/scenario_report_mock.json

python src/agent_cli.py --run-scenarios
# отчёты: data/test_results_ollama.json, data/agent/scenario_report_ollama.json

python src/agent_cli.py --run-scenario recovery_followup        # один сценарий
```

Mock-модель детерминированная. Вызов инструмента она строит по вопросу и истории, ответ собирает из предложений тех фрагментов, которые вернул инструмент. Готовых ответов в ней нет. Она проверяет устройство агента: какие инструменты вызваны и с какими аргументами, как обработаны ошибки, сработала ли проверка ответа. Качество формулировок видно только в прогоне на qwen2.5.

Прогон сценариев на профиле `full` требует флага `--allow-full-profile`. Отчёты предназначены для репозитория, а в полной базе есть ФИО и наименования клиентов.

## Тест-кейсы

Двенадцать сценариев из `config/agent_scenarios.yaml`:

| Тип | Сценарий | Что проверяется |
|---|---|---|
| main | `main_aims` | поиск вызван, в ответе три решения цифрового ядра AIMS, источник `03_aims` |
| main | `main_ergo` | число и список сегментов рынка взяты из фрагмента, источник `01_ergo` |
| alternative | `alternative_not_found` | о стоимости лицензии SIPS в документах ничего нет: ответ «недостаточно информации», сумм нет |
| alternative | `alternative_list_documents` | вызван `list_documents`, перечислены продукты |
| alternative | `alternative_smalltalk` | на приветствие нет ни одного вызова инструментов |
| error | `error_top_k_range` | `top_k=0`: ошибка `invalid_argument` с допустимым диапазоном, один вызов модели |
| error | `error_top_k_type` | `top_k=пять`: ошибка «должен быть целым числом» |
| error | `guardrail_secret` | запрос с API-ключом отклонён до модели, ключа нет в trace и памяти |
| error | `guardrail_empty` | пустой запрос отклонён |
| tool_failure | `tool_failure_index` | коллекции нет: ошибка `index_unavailable`, фактов из документов в ответе нет |
| tool_failure | `tool_failure_llm` | Ollama недоступна: агент ищет без модели и показывает найденные фрагменты |
| recovery | `recovery_followup` | во втором вопросе тема SIPS попадает в поисковый запрос, в ответе 135 км |

Результаты:

| Прогон | Отчёт | Итог |
|---|---|---|
| mock-модель, BM25 | `data/test_results.json` | 12 из 12 |

Тесты способны падать: если отключить в подагенте «Документы» шаблон ответа при ошибке инструмента и подстановку `top_k` из запроса, не проходят 5 тестов из 41 тестов агента. ## Память

Агент помнит 6 последних реплик текущего диалога, каждая обрезается до 500 символов. Этого хватает для уточняющих вопросов. Между запусками история не сохраняется: агенту она для ответов по базе знаний не нужна, а при работе с полной базой сохранённые диалоги стали бы ещё одной копией ФИО и данных клиентов вне индекса. Запросы, отклонённые проверками, в память не записываются.

## Ограничения

- Порог по score для отсечения нерелевантных фрагментов не используется. На этой базе у e5 промах и попадание имеют почти одинаковый score (0,8498 и 0,8575 в замерах из `config/rag.yaml`), поэтому вывод «ответа нет» делают модель и проверка ответа.
- Проверка чисел находит числа, которых нет во фрагментах, но не замечает, если модель приписала верное число не тому кейсу.
- Если в вопросе распознано несколько типов услуг или тегов («стратегия закупок»), берутся карточки с любым из них; применённые фильтры перечислены в первой строке ответа.
- Относительные периоды («за последние 5 лет», «в прошлом году») считаются от текущего календарного года.
- Маршрутизатор перечислений распознаёт отрасль и период по словам и шаблонам. Необычную формулировку он может не узнать, тогда вопрос уйдёт к модели, а она может вызвать `list_cards` сама.
- В одном перечислении показывается до 50 карточек; для больших выборок агент просит уточнить период, отрасль или тип.
- Ответ выводится целиком после всех вызовов модели, без потоковой выдачи.
- Режим `lexical` нужен только для воспроизводимых прогонов: синонимы и перефразирование он не понимает.
- Один пользователь, одна сессия, нет HTTP API и разграничения доступа к полной базе.
- В локальном режиме Qdrant на Windows удаление коллекции может не удалить файл `storage.sqlite`, и новая коллекция подхватит старые точки. `vector_indexer.py` закрывает хранилище перед удалением, проверяет результат и останавливает сборку с понятной ошибкой, если удалить не получилось.
- Сценарии проверяют поведение агента: статус, вызванные инструменты, источники, отсутствие выдуманных фактов. Дословный текст и полноту ответа qwen2.5 они не оценивают.
