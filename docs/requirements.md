# Требования к сервису

Шаг 2 итоговой работы. У каждого требования есть критерий выполнения и способ проверки. В колонке «Baseline» — состояние на теге `baseline-2026-10-02`, подробности в [baseline.md](baseline.md). Контрольные сценарии `CS-NN` описаны в `config/control_scenarios.yaml`.

## Данные для проверки

Все сравнения «до/после» выполняются на одном наборе данных — **`public_v2`**:

- **5 обезличенных PDF** о продуктах, они уже в репозитории;
- **синтетический реестр:** 40 вымышленных карточек проектов и пропозалов, 10 вымышленных сотрудников, те же поля, отрасли и типы услуг, что в настоящих реестрах. Он нужен, чтобы подагент «Реестры» можно было проверить без персональных данных.

Baseline и итоговая версия запускаются на одном индексе `public_v2` с одной моделью (qwen2.5:7b-instruct, temperature 0, seed 42) на одном ноутбуке. Время меряется после прогревочного запроса.

Полная база используется для пилотной проверки. В репозиторий из неё попадают только агрегированные метрики, без вопросов, ответов и имён.

## Функциональные требования

| ID | Требование | Критерий выполнения | Как проверить | Baseline |
|---|---|---|---|---|

| F2 | HTTP API: состояние | `GET /health` возвращает 200 и состояние модели, индекса и каталога; если модель или индекс недоступны — 503 с указанием компонента | автотест с отключённой моделью и индексом | нет |
| F3 | Маршрутизатор подагентов | Каждый запрос получает маршрут `registry`, `documents`, `escalation`, `smalltalk` или `rejected`. Решение и сработавшее правило записываются в trace. Неоднозначные вопросы классифицирует модель | Q2 на контрольном наборе; автотесты правил | правила внутри одного агента, без явного маршрута |
| F4 | Подагент «Реестры» | Перечисления, люди по прошлому ответу, рейтинги, проекты сотрудника — полный список по каталогу, без генерации | CS-05…CS-08, Q4 | есть, только в профиле `full` |
| F5 | Подагент «Документы» | Ответ по фрагментам со ссылками. Фильтр категории или отрасли применяется, только если он подкреплён текстом вопроса (название продукта или синоним); иначе снимается с записью в `warnings` и trace | CS-01…CS-03; автотест на снятие фильтра | модель передаёт неподкреплённый фильтр, регрессия `main_ergo` |
| F6 | Эскалация к человеку | Инструмент `escalate_to_human` создаёт обращение `{id, question, reason, evidence, owner}` в локальной очереди. Пользователь получает статус `escalated`, номер обращения и причину. Срабатывает по правилам E1–E4 ниже | CS-04, CS-12, CS-13, CS-15, Q3 | нет |
| F7 | Память сессии | Уточняющий вопрос с тем же `session_id` использует карточки и тему прошлого ответа; разные `session_id` не влияют друг на друга | CS-06; автотест на изоляцию сессий | есть в CLI, сессий нет |

| F9 | Конфигурация | Модель, temperature, top_k, лимиты, пороги проверки привязки, пути к данным, профиль и ответственные за эскалацию задаются в `config/*.yaml` и переменных окружения. `.env.example` один и актуальный | ревью; автотест загрузки конфигурации | конфигурация есть; два файла `.env.example` / `env.example` |
| F10 | Развёртывание | `docker compose up` поднимает API и Ollama; `GET /health` → 200; CS-01 и CS-05 проходят через API | лог запуска и видео | нет |

### Правила эскалации

| ID | Когда | Причина в обращении | Ответственный (роль из конфигурации) |
|---|---|---|---|
| E1 | Ответ подагента «Документы» не прошёл проверку привязки к источникам после одной перегенерации | `ungrounded_answer` | владелец базы КП |
| E2 | Вопрос из предметной области, но таких данных в базе нет: стоимость, контакты, планы, внутренние оценки | `no_data` | владелец базы КП или реестра, по маршруту |
| E3 | Повторный сбой компонента: индекс или каталог недоступны, либо недоступны и модель, и поиск | `component_failure` | администратор сервиса |
| E4 | Пользователь прямо просит связаться с человеком | `user_request` | по теме вопроса, иначе владелец реестра |

Вопрос вне предметной области («какая погода») не эскалируется: агент вежливо сообщает, что отвечает только по базе знаний.

## Требования к качеству

Цели заданы для контрольного набора `public_v2` (16 сценариев). Baseline измеряется на том же наборе до начала доработки.

| ID | Метрика | Как считается | Цель | Baseline |
|---|---|---|---|---|
| Q1 | Ответы без привязки к источникам | Доля ответов со статусом `answered`, где хотя бы одно предложение с фактом не ссылается на источник или ссылается на фрагмент, с которым у него нет общих значимых слов (порог в конфигурации) | **0%** — основной критерий улучшения | измеряется; известно, что baseline допускает `answered` без ссылок |
| Q2 | Точность маршрутизации | Доля шагов, где маршрут совпал с ожидаемым | ≥ 90% | измеряется по эквивалентам маршрутов baseline |
| Q3 | Эскалации | Полнота: доля сценариев, требующих эскалации, где она произошла. Точность: доля эскалаций, которые были нужны | полнота 100%, точность ≥ 80% | полнота 0%: эскалации нет |
| Q4 | Полнота перечислений | Доля карточек эталонной выборки, попавших в ответ | 100% (без ухудшения) | измеряется |
| Q5 | Исходные 12 сценариев на живой модели | `agent_scenarios.yaml`, qwen2.5 + e5 + Qdrant, `public` | 12 из 12 | 11 из 12 (`main_ergo`) |
| Q6 | Время ответа | Медиана по шагам после прогрева: маршрут `registry` / маршрут `documents` | < 1 с / ≤ 36 с | — / 47 с |
| Q7 | Размер промпта | Медиана промпта шага выбора инструмента у подагента «Документы» | ≤ 900 токенов | 1 373 |
| Q8 | Принудительный поиск | Доля запросов подагента «Документы», где модель не вызвала инструмент сама | не выше baseline | измеряется (в прогоне 12 сценариев — 3 случая) |
| Q9 | Автотесты | `pytest` в минимальном и полном окружении; покрыты маршрутизатор, эскалация, проверка привязки, снятие фильтров, API | все проходят | 99 тестов, API и эскалации нет |

Улучшение считается подтверждённым, если Q1 достигает цели, а Q4, Q5 и Q6 не ухудшаются относительно baseline.

## Требования безопасности

| ID | Риск | Критерий выполнения | Как проверить | Baseline |
|---|---|---|---|---|
| S1 | Секреты и ПДн в репозитории | Автоматическая проверка: шаблоны ключей API, токенов, ФИО вне списка синтетических имён, внутренние коды проектов. Находок нет | тест `test_repository_hygiene.py` в `pytest` | проверки нет; реальная фамилия была найдена вручную и вычищена из истории |
| S2 | ПДн и секреты в логах | В логи пишутся `request_id`, маршрут, статус, коды ошибок, длительность, число источников. Текст вопроса и ответа не логируется | автотест: вопрос с ФИО и тестовым ключом не появляется в логе | структурированных логов нет; trace сохраняется только по флагу |
| S3 | Секреты в запросе | Запрос с секретом отклоняется до модели и не попадает в память, лог, trace и очередь эскалаций | CS-16; автотест | блокировка до модели есть, логов и очереди нет |
| S4 | Утечка внутренней информации в ошибках | Ответ API на внутреннюю ошибку — код и понятное сообщение, без traceback, путей и конфигурации; подробности только в логе | автотест с принудительным исключением | в CLI исключения перехватываются |
| S5 | Некорректный ввод | Пустой вопрос, длиннее 1 000 символов, не строка, некорректный JSON → 400/422 с понятным сообщением, сервис продолжает работать | автотесты API | guardrails есть в агенте, API нет |
| S6 | Сбой внешних зависимостей | Модель недоступна → `degraded` с найденными фрагментами. Индекс или каталог недоступны → эскалация E3. `/health` показывает компонент. Сервис не падает | CS-14, CS-15; автотесты | деградация есть, эскалации нет |
| S7 | Небезопасный ответ | Нет уверенного ответа без источников (Q1). Вопросы о данных, которых нет в базе, эскалируются, а не дополняются догадками (E2) | Q1, Q3 | `answered` без ссылок возможен |
| S8 | Полная база вне внутреннего контура | Профиль `full` не входит в Docker-образ (подключается томом). Отчёты по `full` в репозитории содержат только агрегаты. Очередь эскалаций и trace в `.gitignore` | ревью `.dockerignore`, `.gitignore`; S1 | `.gitignore` есть, образа нет |

## Требование к процессу

**R1.** Любое изменение промпта, схемы инструментов или маршрутизатора проверяется прогоном контрольного набора **на живой модели**, а не только `pytest` на mock-модели. Основание — регрессия `main_ergo`: изменения схемы инструментов сломали простой вопрос, и ни один из 99 тестов этого не заметил.
