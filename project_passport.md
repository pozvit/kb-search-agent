# Паспорт проекта: KB Search Agent

Версия от 05.10.2026. Траекторию и объём нужно согласовать с экспертом в течение первой недели.

## 1. Бизнес-задача и ожидаемая польза

В консалтинговой компании опыт проектов разбросан по трём источникам:

- реестр проектов и реестр пропозалов (два файла `.xlsb`, после очистки 1 074 карточки);
- 486 коммерческих предложений в PDF;
- описания продуктов.

Чтобы подготовить новое коммерческое предложение, консультант вручную ищет похожие проекты по отрасли, типу услуги и годам. Затем выясняет, кто в них участвовал, и достаёт подходящие формулировки из прошлых КП. Реестры при этом читаются плохо: бинарный Excel, матрицы тегов, разные классификации отраслей.

Сервис отвечает на такие вопросы за один запрос:

- какой у компании опыт по отрасли, услуге, периоду;
- кто из сотрудников этот опыт имеет;
- что именно говорилось в прошлых предложениях.

Ответ сопровождается ссылками на карточки реестров и фрагменты документов.

Ожидаемая польза:

- **Быстрее подбор референсов к КП.** Сейчас это 1–2 часа на одно предложение (оценка пользователей), цель — несколько минут, включая проверку источников.
- **Полнота.** Перечисление по отрасли или услуге возвращает все подходящие карточки, а не первые найденные.
- **Проверяемость.** У каждого утверждения в ответе есть источник, который можно открыть.

## 2. Целевой пользователь и сценарий

**Основной пользователь:** консультант или специалист по пресейлу, готовящий коммерческое предложение. Ему нужны релевантные референсы, команда, которую можно указать в КП, и формулировки из прошлых предложений.

**Вторичный сценарий:** подбор экспертов под новый проект (рейтинг сотрудников). Он нужен и пресейлу, чтобы сформировать команду в КП, но отдельно не оптимизируется.

Типичный сценарий:

1. «Какие проекты были в медицине за последние 5 лет?» — полный список карточек проектов и пропозалов с годами и клиентами.
2. «Кто выполнял эти проекты?» — команда, партнёр и сотрудник по каждой карточке из прошлого ответа.
3. «Кто делал больше всего проектов в операционной эффективности?» — рейтинг людей с числом проектов и пропозалов.
4. «Как мы описывали подход к диагностике закупок?» — ответ по фрагментам прошлых КП со ссылками на документы.

## 3. Входные данные, результат, ограничения

| | |
|---|---|
| **Вход** | Вопрос на русском языке, до 1 000 символов. Профиль базы: `public` — 5 обезличенных PDF для демонстрации и тестов; `full` — рабочая база, только во внутреннем контуре |
| **Данные** | Профиль `full`: 1 074 карточки реестров (586 проектов, 488 пропозалов), 486 PDF коммерческих предложений, 5 PDF продуктов, около 23 400 чанков в Qdrant. Профиль `public`: 49 чанков |
| **Результат** | Ответ, статус (`answered`, `not_found`, `rejected`, `error`, `degraded`, `smalltalk`), источники (карточка или документ, год, отрасль), предупреждения проверки ответа, trace |
| **Ограничения** | Развёртывание локальное (Docker на ноутбуке), один пользователь, без авторизации. Локальная модель qwen2.5:7b-instruct на CPU. Только русский язык. Полная база содержит ФИО сотрудников и наименования клиентов, поэтому работает только во внутреннем контуре, без публикации данных и отчётов. ## 4. Исходная версия (baseline)

**Фиксация:** состояние репозитория `pozvit/kb_agent` на 02.10.2026 — последний коммит этого дня, отмеченный тегом `baseline-2026-10-02`. Это домашнее задание модуля «ИИ-агенты» вместе со всеми доработками, сделанными до начала дипломной работы. Работа получила зачёт.

### Что реализовано

| Компонент | Состав |
|---|---|
| Агент | CLI, tool calling через Ollama (qwen2.5:7b-instruct). Guardrails до вызова модели: пустой ввод, длина, секреты. Принудительный поиск, если модель не вызвала инструмент. Деградация при недоступности модели. Шаблонные ответы при ошибке инструмента |
| Инструменты | `search_knowledge_base` — семантический поиск e5-small + Qdrant с фильтрами по категории, отрасли и годам. `list_documents`. `list_cards` — выборка из каталога карточек по отрасли, типу услуги, детальному тегу, сотруднику и периоду, рейтинг людей (`group_by=people`) |
| Маршрутизатор | Перечисления, вопросы о людях по прошлому ответу, рейтинги и вопросы о проектах сотрудника отвечаются по каталогу без вызова модели. Отрасль, услуга и период распознаются по синонимам и шаблонам, включая относительные периоды |
| Память | 6 последних реплик и карточки, на которые ссылался прошлый ответ (для «кто делал эти проекты») |
| Проверка ответа | Ссылки `[Фрагмент N]` только на реально найденные фрагменты, числа в ответе сверяются с текстом фрагментов, фраза «нет информации» даёт `not_found` |
| Данные | Конвейер реестров: `.xlsb` → CSV → карточки с метаданными. Лист `checked` исключён: происхождение данных не подтверждено |
| Проверка | 99 тестов pytest; 12 YAML-сценариев с ScenarioRunner и evaluator; воспроизводимый режим без Ollama и модели эмбеддингов (mock + BM25) |

Метрики качества на полной базе снимаются на контрольном наборе вопросов (этап «Требования»): на теге baseline и на итоговой версии.

### Известные ограничения baseline

По отзыву эксперта на домашнее задание:

1. **Привязка к источникам мягче, чем заявлено.** Ответ без единой корректной ссылки получает статус `answered`, только с предупреждением. Проверяются существование ссылок и числа, но не нечисловые утверждения.
2. **Скрытое усечение запроса.** Поисковый запрос длиннее 500 символов молча обрезается, хотя README говорит о проверке. Пользователь этого не видит.
3. **Evaluator опирается на подстроки, статусы и вызовы инструментов.** Неполный или неверный по смыслу ответ с нужными ключевыми словами он не заметит.
4. **Центральный контур агента теряется** среди инфраструктуры RAG-пайплайна.

По собственной проверке:

5. **Медленный и нестабильный путь через модель на полной базе:** 125–175 с; частые `forced_search`; некорректный формат ссылок.
6. **Нет сервисного слоя:** HTTP API, структурированного логирования, контейнера.

## 5. Цель развития и траектория

**Основная траектория: ИИ-агенты.** RAG — дополнительный компонент: он подключён к агенту как инструмент поиска.

Цель — превратить CLI-прототип в пилотный сервис и сделать агентный контур строже и прозрачнее. Объём не расширяется: новых источников и инструментов не будет, только надёжность и проверяемость существующих.

1. **Строгая привязка к источникам.** `answered` — только при корректных ссылках. Ответ без ссылок перегенерируется один раз, иначе получает отдельный статус. Каждое предложение с фактом сверяется с процитированным фрагментом. Документация описывает фактическую строгость проверки, без преувеличений.
2. **Прозрачность.** Усечение запроса и любые изменения аргументов видны в ответе и в trace.
3. **Структурированная оценка.** Контрольный набор из 15–20 вопросов по полной базе (внутренний) и по `public` (в репозитории). Ожидаемые карточки и документы задаются по идентификаторам. Метрики:
   - полнота перечислений;
   - доля ответов, где каждое утверждение подкреплено источником;
   - доля `forced_search`;
   - время ответа.

   Сравнение baseline и итоговой версии.
4. **Путь через модель на полной базе.** Меньше `forced_search` и ответов без ссылок, ниже время ответа за счёт размера контекста. Улучшение подтверждается метриками пункта 3.
5. **Сервисный слой:**
   - FastAPI: `POST /ask`, `GET /health`;
   - конфигурация в YAML и переменных окружения;
   - обработка ошибок, включая внутреннюю ошибку и недоступность модели;
   - структурированные логи без ПДн и секретов.
6. **Развёртывание.** Локально в Docker на ноутбуке: Dockerfile и docker-compose (API + Ollama). Эксперт проверяет на профиле `public`; полная база подключается томом и в образ не входит. После запуска выполняется контрольная проверка через API.
7. **Читаемость контура.** Центральный сценарий агента выделен в README и в структуре кода, вспомогательный RAG-пайплайн описан отдельно.
